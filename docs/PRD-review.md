# Agent Voucher PRD v3.0 对抗性审查

日期：2026-08-23

审查对象：[`PRD.md`](PRD.md) v3.0

审查范围：冻结 Phase 1/2 基线，以及唯一未完成的 Phase 3 企业凭证闭环

需求结论：**GO——v3.0 已把范围、数据合同、金额守恒、真实 LangGraph 和验收门禁冻结为可实施需求**

实现结论：**GO TO G2——Phase 3 尚未实现，但审批字段、凭证要素、固定 XLSX 和金蝶草稿保存/回查合同已直接复用 Auto_Voucher，合同门禁不再阻断架构与实现**

## 1. 审查方法与证据边界

本次审查采用减法审查、失败路径审查和独立反方审查，重点攻击以下问题：

- 是否把“自有企业可运行”再次扩张为平台、插件、通用 Connector 或 ERP 生态；
- 是否把 Auto_Voucher 的参考实现误当成完整规范或代码复用授权；
- 可视化画布是否可能只是导航页面，而没有形成可执行 `WorkflowDefinition`；
- LangGraph 与现有 JobRunner 是否形成双编排，或把 checkpoint 误当成业务真值；
- N:N/任意部分匹配是否可能重复占款、超额分配、丢失 Residual 或重复生成凭证；
- 输入 Revision 变化、崩溃重试、并发确认和人工自确认是否有可验证边界；
- 凭证字段和列顺序是否确实直接采用 Auto_Voucher，而非重新发明；
- 金蝶外部写入是否严格发生在人工确认后、只保存草稿并完成幂等回查；
- “文档/草稿/模拟通过”是否可能被误报为已实现或可生产运行。

审查只评价需求质量。现有代码、构建、模拟 Adapter、截图或本文件本身均不能证明 Phase 3 已完成。

## 2. 冻结基线复核

### 2.1 保持不变

- A01 访问与工作区、A02 运行与审计；
- A03 本地/飞书来源归档、A04 证据库；
- A05 银行 CSV/XLS/XLSX 解析和文字层发票 PDF 提取；
- Windows 10 22H2、Node.js 24、单实例、单 Writer、审计、Doctor、备份恢复 v2；
- Phase 2 实现 revision `8a2a7f5e56f1dceab285a73676658191caa82cc6`、验收证据 revision `85fcb0b` 和候选 tarball SHA-256 `98baf421678a21b8328febfd4bcf8d7d98ed7af7926d70869db71f8bb523820a`。

Phase 2 的 GO 只表示来源、证据、有限解析和恢复可进入 Windows 10 局域网试点，不表示业务 LangGraph、匹配、凭证或企业生产闭环已完成。原 v2.0 审查中的 LAN HTTP、无静态加密、Permission Model 非完整沙箱、Credential Manager 桌面会话和真实混合负载残余风险继续有效，未被 v3.0 宣称为已解决。

### 2.2 明确未完成

- 当前 LangGraph 只有 `validate_runtime` smoke 节点，不是业务编排；
- 没有可视化工作流定义、编译器或业务节点；
- 没有 `ApprovalRecord v1` 持久化、N:N Allocation、VoucherDraft、固定模板导出或 Agent Voucher 内的金蝶推送；
- A01 的 `cfg_legal_identity` 仅作为经过迁移、权限、Revision CAS 和审计测试的内部配置能力进入候选；它没有 Phase 3 UI，也不代表匹配、凭证或 OCR 已实现。此前未使用的 `@napi-rs/canvas` 和 `tar` 直接依赖已从发布候选移除。

## 5. P2 与已接受约束

- 工作流布局与执行语义分离；移动节点不产生业务版本，改参数或边必须产生新版本；
- 三个新增页面仍需键盘、焦点、非颜色表达、200% 缩放和长内容验证；
- 自动候选为空是正常业务状态，不得制造虚假异常或匹配；
- 已导出的匹配组不在本阶段自动反转，避免隐含冲销和外部状态修改；
- 现有 LAN HTTP、无应用级静态加密和 Windows Credential Manager 桌面限制继续作为已接受残余风险；
- 不要求借 Phase 3 升级数据库、引入事件总线、改造成服务化架构或建设平台运维能力。

## 6. 范围审计

### 6.1 Phase 3 唯一允许

- 已验证银行流水和已确认飞书 `APPROVED` 审批；
- 七类固定可视化节点和真实 LangGraph；
- `MatchGroup + Allocation + Residual` 的 1:1、1:N、N:1、N:N 与部分匹配；
- 确定性规则、活动主数据校验、凭证草稿、人工确认；
- 一个固定模板、人工确认后的金蝶云星空凭证草稿 Save/回查，以及一个单企业/单账套 Windows LAN 运行边界。

### 6.2 默认拒绝

- OCR、更多文档/来源、银行 API、税务平台；
- 模型会计判断、RAG、多 Agent；
- 任意脚本、插件、自定义节点、通用 Connector；
- 外币匹配、容差、退款/冲销自动化；
- 第二模板、模板设计器、其他 ERP、通用 ERP Connector，以及金蝶自动提交/审核/过账；
- 多企业、多账套、SaaS、公网、移动端；
- 自动提交、审核、过账、付款、报税或结账。

## 8. 最终结论

PRD v3.0 已把最新要求收敛为一条可执行、可停止的企业内部凭证闭环，需求层面 P0/P1 已有明确处置，**需求质量 GO**。

Phase 3 代码仍未实现，但字段、凭证和金蝶草稿推送合同已经按用户要求直接复用 Auto_Voucher。当前实施结论为 **GO TO G2**：可以进入架构和模块实现；这不代表 Phase 3 已完成、金蝶已接通或企业闭环已验收。

本审查通过不授权提交、push、发布、部署、生产切换或对外宣传，也不允许以“风险缓解”名义新增本 PRD 未列功能。
